## Real owner and MFA

The authorized synthetic Super Admin is for demonstration and must not be renamed or silently promoted into the real owner. Obtain the owner's explicitly chosen verified account identity and approval for the intended environment. Verify it through the existing provider/account process; do not match a family or grant privilege using an email string alone.

For a fresh environment with no Super Admin, `scripts/bootstrap-admin.mjs` accepts an explicitly supplied existing verified account and calls the database's single-bootstrap boundary. The script reads private server configuration. Its presence does not authorize running it against an arbitrary project. The current staging environment already has a synthetic Super Admin; the bootstrap is not an owner replacement tool and should refuse a second bootstrap. Owner handover needs a separately approved privileged procedure that preserves audit attribution, verifies the real identity, assigns only the necessary roles and explicit financial grants, and retires synthetic access where appropriate.

The real owner must enroll their own authenticator and prove AAL2 access, then test denial at AAL1 and immediate revocation on a separate session. Role selection in the interface is not authorization. Preserve current-record role/branch checks, guardian scopes and separate financial privileges. Never share the demonstration password as an operational credential. Lost-authenticator recovery requires documented identity verification and authorized provider administration; do not add an application MFA bypass. Record who can perform recovery and test recovery without publishing any factor secret or backup credential.

Run `node scripts/verify-local-restore.mjs` to repeat this isolated local check; evidence is in the private `outputs/local-restore/2026-09-20T01-05-56-674Z/evidence.json`.

That pass covers database schema/data on the running local PostgreSQL infrastructure. It does not cover hosted backups/PITR, cluster globals, provider/Auth configuration, Worker boot, restored Storage object bytes or deployment rollback. The following broader recovery acceptance still applies.

The recovery owner must first approve recovery-point and recovery-time objectives, retention, encrypted storage, access control and the isolated rehearsal environment. Confirm the project's actual backup/PITR availability and retention in the provider; do not assume the current plan includes either. Supabase database backups do not include Storage object contents, so preserve private files separately and reconcile them with database metadata. Custom role credential restoration also needs separate handling. See [Supabase backup documentation](https://supabase.com/docs/guides/platform/backups).

Before a schema release or customer cutover:

1. Inventory recoverable assets: database application/private/Auth state and migration history; RLS, function grants and extensions; private Storage objects and bucket policies; deployment artifact/source commit/lockfile; provider Auth/redirect/template configuration; secret-store versions and integration flags. Record what each backup actually contains and excludes. Never place secrets or raw family exports in the repository.
2. Capture an approved backup/export and source checksums into encrypted restricted storage. Use the provider's supported backup workflow and version-appropriate CLI, discovering flags with `supabase --help` and `supabase db dump --help`. Follow the current [Supabase CLI backup/restore guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) for database roles/schema/data handling; do not paste connection strings into logs or run an unreviewed dump as though it includes every managed schema.
3. Restore into a separately authorized, isolated destination, never over staging or production as a rehearsal. Keep outbound email, webhooks, notifications, payment adapters, telephony and scheduled dispatch disabled before allowing any restored worker to start. Ensure copied URLs/keys cannot reconnect it to the source database or live provider.
4. Verify schema/migration version, table and entity counts, referential integrity, RLS and function grants, append-only audits/ledgers, exact commercial balances, bookings/capacity, entitlements and private file checksums. Prove unrelated parent/branch/coach denial with separate sessions. Check authentication/MFA recovery against the actual restore mechanism; do not assume existing sessions remain valid.
5. Boot the matching compiled Worker with isolated configuration and run the synthetic connected journey. Compare restored financial and migration control totals against the pre-backup snapshot. Investigate any missing Storage objects or Auth configuration before acceptance.
6. Record backup identifier/time, destination identity, checksums, start/end times, observed data-loss window, test results, exceptions and reviewer. Approve retention/destruction of the rehearsal copy. Mark restore readiness verified only after this evidence exists; a successful backup download or empty-database migration replay is insufficient.

## Source and deployment rollback

Before deployment, retain the last accepted source commit, compiled artifact, provider deployment identifier, schema compatibility range, runtime-configuration version and rollback owner. Verify the new Worker against additive migrations locally first. The existing owner-only audience must remain in place during staging releases.

If a release fails, record the failure and pause affected mutation entry points and external dispatch. Revert application traffic to the last accepted provider revision only after checking that it is compatible with the currently applied database schema. For a source rollback, create a reviewed revert commit or redeploy the preserved immutable revision; avoid a destructive reset of a shared working tree. Restore compatible runtime configuration without printing secrets, then verify HTTPS, cache/cookie behavior, MFA, scoped reads and a synthetic persisted mutation on the actual Worker.

Application rollback does not undo database writes. Do not delete migration history or use `supabase db reset` against a hosted project. Prefer a reviewed forward correction for additive schema faults. A destructive schema/data recovery requires the authorized backup/restore procedure, an impact window and independently reconciled post-backup changes. Keep audit and posted financial history intact. For a customer import, use the future approved batch-specific reversal process described in [MIGRATION.md](MIGRATION.md); it is not implemented by the dry-run planner.

Record both the source/deployment revision restored and any schema/data state that remains ahead. Resume operations only after permission, financial, capacity and file checks pass. Retain the incident evidence and obtain operator acceptance of any unresolved reconciliation.

## External delivery activation and failures

Use [ACTIVATION-REGISTER.md](ACTIVATION-REGISTER.md) to track accountable owner, evidence and required authorization per integration. Activation must begin with approved test recipients/sandbox resources and measured results. Queue creation, provider acceptance and confirmed delivery are different states; retain provider event IDs and redacted failure details. A retry must preserve idempotency and avoid double financial allocation or duplicate messages.

For SMTP, verify sender ownership, account and quota, exact redirect URLs, recipient restrictions and real inbox receipt before enabling hosted signup. Exercise signup confirmation, password recovery, staff/guardian invitation, expiry/replay and account-link authorization on the actual HTTPS deployment. A local captured email does not prove real delivery. Record a disable/rollback path before changing flags. WhatsApp, push, telephony and payment activation have separate recipient/number/browser/provider and policy requirements; SMTP success cannot establish their readiness.

## Monitoring and incident record

Before live operation assign an operator and alert destination for failed authentication/MFA, permission denials, database/API errors, Worker failures, rate limits, capacity conflicts, ledger reconciliation differences, backup failures, file-access failures, outbox retry exhaustion and unexpected external deliveries. Check frequency and escalation ownership must be approved; no monitor or scheduler is installed by this document. Keep actor/entity/provider identifiers and timestamps, with minimal redacted context; avoid passwords, tokens, family text or medical details in logs.

On an incident, preserve evidence, disable only the affected capability, verify current scope and investigate through least-privileged operator access. For suspected credential compromise revoke affected sessions/credentials through the approved owner procedure and re-test current-record access. Recovery completion requires a working scoped user journey and reconciled durable state, not merely a green process health check.
