# Durable synthetic in-app work

This slice executes due in-app broadcasts, seven-day renewal reminders and expired waitlist offers. It does not send email, WhatsApp or push, charge money, renew a contract, book the next child, or generate monthly reports. The migration creates **no approvals, cron extension or scheduled job**. Root applied this migration additively to the verified `cwdazidovxqeevmpicng` staging project after review (30 hosted migrations at that point). No owner approvals or cron activation were installed. Hosted autonomous execution remains unverified and requires the separate activation gate below.

## Authorization and execution

`public.scheduler_configure` is an invoker wrapper around a narrow private function. It requires an active current Super Admin and actual AAL2. The validated session issuer must equal the selected environment (`http://127.0.0.1:56321/auth/v1` locally or `https://cwdazidovxqeevmpicng.supabase.co/auth/v1` for the one approved staging project). Enabling also requires a protected `branches.synthetic=true`, active, confirmed branch. Approval history is immutable. A string claiming `target_ref` does not replace these checks.

`private.run_scheduled_jobs(target, limit)` is executable by its database owner, not anon, authenticated or service-role API clients. It rejects a non-null `auth.uid()`. It never sets JWT claims or impersonates an owner. Each tick rechecks current branch state and the approving owner's active Super Admin role. Removing authority or appending a disabled approval stops subsequent work. A human approval authorizes this unattended system action; it does not manufacture a recurring human AAL2 session.

For every broadcast chunk it rechecks the original creator's active Head Office role and existing broadcast capability for that branch. Super Admin follows the existing capability model; an Admin requires its explicit grant. Coach, Sales and Branch do not become broadcasters through a capability grant. The reviewed recipient set is an upper bound: current family-branch links, guardians, active parent roles and latest contact consent for marketing are rechecked. A new guardian is not silently added to an old reviewed batch. Both family and recipient profile must retain protected synthetic markers.

Automatic reminders are narrower than the older manual queue: only **active**, unrenewed memberships expiring from today through seven Dubai calendar days qualify. Pending, frozen, suspended and already expired memberships are skipped. Family-branch, synthetic family/child, package policy and current active synthetic guardian-parent recipients are rechecked. The unique membership reminder and unique product event/notification keys prevent duplicate reminders; no invoice, payment or entitlement is created.

Expired offers are marked expired for synthetic children/families and retained in an explicit staff-review queue. They already cease counting as held capacity at expiry in existing availability checks. The worker never chooses the next child: staff use the existing offer command, which rechecks current eligibility/capacity. Historical expiry review items remain visible as historical work; no automatic staff acknowledgement is inferred.

## Durability, limits and observation

The worker shares the operational advisory transaction lock with foreground mutations. A contending tick returns `busy`; it does not process the same work concurrently. Discovery queues at most 50 new items per kind. A tick processes 1–25 jobs, and a broadcast item resolves at most 100 recipients before durable continuation. Each item commits its effects, state and append-only attempt record together. A database exception rolls back that item, retains only SQLSTATE, and retries after 30, 60, 120 and 240 seconds; the fifth consecutive failure stops in `failed`. No raw exception body, family text or credentials enter run logs. Transaction/server failure before commit leaves the prior durable state and is retried by a later cron tick.

System product events have a null human actor. `scheduled_job_effects`, `scheduled_job_runs`, immutable approval records and redacted `SYSTEM_JOB` audit rows link each effect to its job, approving owner and original broadcast creator. This is explicit system causation, not unattributed staff impersonation. External outbox entries remain `not_configured`, with zero send attempts.

The MFA Super Admin Security panel reads `GET /api/jobs` through the cookie-scoped client. It shows effective approval separately from installed active cron, pending/retry/failed/staff-review counts, the real last successful item and latest 50 attempts. Errors clear the displayed snapshot; denied access is not represented as a healthy inactive scheduler. It has no run/enable button. SQL status reads can inspect the complete private queue; the UI's 50-row history limit does not imply a complete export.

## Explicit staging activation gate

Do not run this section automatically during deployment or migration replay. Root must review the exact target **cwdazidovxqeevmpicng**, synthetic branch provenance, templates and audience, then arrange a real owner AAL2 approval. The approval script uses an existing genuine session and never acquires a password, manufactures a token, elevates AAL or bypasses MFA.

1. Put the publishable key and an existing, unexpired, real owner AAL2 `KAFOU_OWNER_ACCESS_TOKEN` in a private mode-0600 environment file. Do not paste the token into arguments, logs or documentation. `SUPABASE_URL`, if present, must exactly match the selected target. The script rejects service/secret keys, mismatched issuer and non-owner authority and verifies the token with the actual Auth provider.
2. Run the read-only check with the intended branch UUID: `node --env-file=<private-file> scripts/jobs/approve.mjs --staging --branch=<uuid>`. This verifies protected synthetic provenance from that exact project's database. It makes no approval or cron write.
3. After review, use the same command with `--approve --confirm-synthetic-staging --reason="Reviewed synthetic in-app scheduler activation"`. Record the returned approval ID. Without that genuine owner approval, stop here. A SQL-created test approval is not a substitute.
4. With the database tool explicitly targeted at `project_id=cwdazidovxqeevmpicng`, review and execute [install-staging-cron.sql](../../scripts/jobs/install-staging-cron.sql). Its database guard requires a current validated owner approval for this exact target and synthetic branch. It installs/uses pg_cron and schedules `kafou-synthetic-inapp` once per minute. Do not execute against a linked/default project by assumption. Verify provider project identity in the tool, not from the common `postgres` database name.
5. Verify two real intervals in `cron.job_run_details`, actual in-app results and repeat idempotency, plus `public.scheduler_status()` in the real owner session. Confirm all external outbox statuses/attempts remain disabled. Hosted cron success must be recorded separately from the local proof.

Pause by the same real-owner approval script with `--pause --confirm-synthetic-staging --reason="Pause for operator review"`; or, for immediate operational stop, the database owner runs `select cron.unschedule('kafou-synthetic-inapp');` on the exact approved project. Retain historical job records. Do not reclassify failed/cancelled jobs as delivered. After diagnosing a failed item, a reviewed database-owner transaction may requeue that single UUID, record a redacted manual-retry audit reason and set `next_attempt_at=now()`; all authority/eligibility checks execute again. Do not bulk reset attempts or restore revoked creator authority to force delivery.

After a restore, **keep cron disabled before the restored database starts processing**: copied approvals are data, not fresh authorization for another environment. Do not restore or enable provider cron jobs as part of data reconciliation. Review log growth/retention and assign an operator before sustained operation. No external delivery or alerting provider is configured by this slice.
