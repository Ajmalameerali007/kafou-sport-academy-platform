# Coaching, development and private certificates

## Connected workflow

Head Office/Owner with `development.configure` creates immutable sport/level criteria versions. A version contains 1–20 uniquely named numeric metrics, localized labels, units, minimum/maximum and direction. Old assessments retain their exact standard version. Criteria are configurable; this implementation makes no claim that synthetic criteria are approved academy standards.

A currently assigned coach writes a private session plan and saves an assessment for a linked child on that session's non-cancelled roster. The class, sport and criteria level must match, and assessment entry starts only once the session has started. Drafts may omit metrics; submission requires every metric and validates the exact version's range. Submitted evidence is locked. An independent Head Office/Owner with `development.review` approves or returns it; approved evidence requires `development.publish` before the family sees it. Rejected assessments can be edited and resubmitted with retained review history.

Internal notes live in a separate table. Neither a published assessment nor a certificate exposes them. Internal review reasons and session plans are also excluded from family RLS. Draft parents, unrelated families, revoked coaches, and unassigned coaches are denied.

Publication appends measured results with their original unit, metric name, criteria version and measurement date. Personal bests compare within the same child, criteria version, metric and direction; no synthetic percentage or cross-sport comparison is created. An approved recommendation appends sport-specific level history and updates only that sport profile. It does not move the enrollment or class. A stale recommendation is denied if the current sport level changed.

Monthly reports reference existing published assessments for the same child, sport and Dubai calendar month. Creating another report for the month creates another version. Reports follow draft → submission → independent review → publication. The engagement extension adds factual draft generation and author-only editing of draft/returned summaries; review history is retained. Publishing another report for the month retains prior versions. Published reports are immutable.

Certificates are immutable issue snapshots from published assessment evidence. An authorized certificate grant is required. Revocation is append-only and removes the issue from certificate SELECT RLS; subsequent download requests cannot access the revoked row. The correction extension adds sequential certificate reissues with a new reference, its own family-facing correction reason and an explicit link to the replaced issue. Reissuing a live certificate withdraws that issue atomically; reissuing an already withdrawn certificate preserves its original withdrawal reason. An old issue cannot acquire two replacements. Existing downloaded copies cannot be remotely deleted. The renderer does not fetch or authorize records itself: the root API must query `development_certificates` using the current user's RLS client before rendering.

Authorized independent reviewers can reverse the latest effective approved progression with a family-facing reason. The reversal appends an immutable decision, restores the preceding active sport level, and withdraws certificates associated with that assessment. Original published evidence and approval history remain intact. No class enrollment is created or changed. A stale reversal cannot overwrite a different current level; an already reversed recommendation cannot be approved again. A new assessment is required for a future progression decision.

## Training guidance

A next training target is an optional, bounded field on the assessment itself. The assigned coach drafts it alongside scores and supporting summary; submission locks it, independent academy review approves or returns it, and publication makes it visible to the owning family. Published targets are immutable with their evidence. This remains a practical next-step note; the independently tracked measurement workflow below records completion separately.

Current safety instructions are separate from internal notes and family documents. A current guardian can write or clear the instruction for their child. Head Office/branch operations need the explicit `development.safety` capability and relevant family branch relationship; a global Head Office grant or verified Owner can manage all children. Sales and coaches cannot edit this field. Current assigned coaches and active substitutes can read instructions only for children rostered in non-cancelled, active-class sessions ending within the previous day or starting within the next 45 days. Historical assignments, revoked substitutions/branch access and unassigned siblings do not authorize access.

The field is limited to 1,000 characters of current practical training guidance. Clearing replaces the current value; no medical-history collection or coaching history feed is created. Metadata audits contain record IDs, never instruction text. Synthetic tests contain only benign practice-area examples.

## Emergency contact policy

Migration `20260920012626_product_coach_emergency.sql` adds an immutable, versioned branch policy. Visibility is disabled when no policy exists. Head Office/Owner with `development.configure` must explicitly acknowledge the synthetic policy and choose a lead window of 0–360 minutes; a disabled newest version never falls back to an older enabled version. Production academy approval is not implied by synthetic configuration.

The guardian saves or corrects the existing family emergency contact using `community.contact.save`. Coaches never gain raw family-contact SELECT access. The invoker view `development_coach_emergency_contacts` calls a fixed-search-path, explicitly authorized function and returns only roster/session/child identifiers for context plus the contact name, phone and relationship. It requires the exact active roster, current class coach or active unrevoked substitute, current branch access, an active branch/class, a non-cancelled session, and the configured time window. Visibility ends at session end. Sales is denied even on a mixed coach account. No historical phone directory, family/guardian identifiers, email, notes or contact notifications are exposed.

`development.emergency.policy` accepts `{branch_id, enabled, minutes_before, synthetic_acknowledged: true}`. `DevelopmentEmergencyPanel` shows assigned-session contacts in Coaching and policy history/configuration in Criteria. It uses existing permission names; no permission picker change is required.

## Independently tracked targets

Migration `20260920013226_product_training_targets.sql` adds `development_targets`, append-only `development_target_reviews` and append-only `development_target_events`. A currently assigned coach selects a real published baseline measurement for their rostered athlete and sport, sets a bounded title, an improved target in the exact versioned metric range, and a Dubai calendar target date within 366 days. One active target is allowed per child/criterion version/metric. A returned draft can be revised and resubmitted; baseline/context ownership remains immutable.

The lifecycle is draft → submitted → approved → published. Review requires an independent Head Office/Owner with `development.review`; publication requires `development.publish`. Parents see only targets with a publication timestamp. Internal review reasons are kept in a separate table and never exposed to families. The published plan, baseline and target value cannot be rewritten.

Completion is a separate claim: the current assigned coach selects another published result for the same athlete, exact criterion version, metric, unit and direction. Its measurement must be later than the baseline, its assessment must have been published at or after target publication, and its value must reach the target. An independent reviewer approves or rejects completion; submission alone is not achievement. Rejection returns the target to active and retains private review history. An authorized publisher can withdraw a published/completed target with an explicit family-facing correction reason, preserving the original plan and completion history. No cash, rewards, certificate or class enrollment is granted automatically.

Commands are `development.target.save` (`{id?, session_id, baseline_result_id, title, target_value, due_on}`), `.submit`, `.publish` (`{id}`), `.review` and `.completion.review` (`{id, decision: approved|rejected, reason}`), `.completion.submit` (`{id, result_id}`), and `.withdraw` (`{id, reason}`). All use the existing development dispatcher and request idempotency. Existing `development.review`/`development.publish` grants apply. `DevelopmentTargetsPanel` is shown in Coaching and Progress, follows athlete/sport filters, and includes draft editing, evidence selection, independent reviews, withdrawal and history in English/Arabic.

## Integration contract

- `private.development_command(action, jsonb)` is callable only through root `public.product_command`, which supplies transaction/idempotency handling. All commands independently recheck authorization.
- Correction commands: `development.level.reverse` accepts `{id: history_id, reason}` under `development.review`; `development.certificate.reissue` accepts `{id: certificate_id, title, reason}` under `development.certify`. Both require Head Office/Owner and published evidence.
- `development_level_reversals` exposes immutable public correction reasons. `development_certificate_records` exposes authorized certificate history, including withdrawn snapshots, version, predecessor, reason and branch. This invoker view delegates to a narrowly authorized, fixed-search-path private read function. It must never be used for PDF download authorization: only the base `development_certificates` RLS query provides that decision.
- Migration `20260920003746_product_development_history.sql` wraps the original private dispatcher, retaining all original actions. Root should regenerate types for the new table/view and certificate `version`/`replaces_id` columns.
- Guidance commands: `development.safety.save` accepts `{child_id, instructions}` (blank clears); `development.assessment.save` now accepts optional `next_target`. Both fields are limited to 1,000 characters by SQL and the request validator.
- `development_safety_children` is an invoker view over a narrowly authorized, fixed-search-path private read function. It projects of child ID/name, current instructions, update time and server-derived `can_edit`. It includes authorized children without an existing instruction so the UI can create one. The underlying `development_safety_instructions` table allows current family/authorized operations reads and has no direct mutation grant. Coaches use only the explicit projection, which omits the guardian author ID and family identifiers. `DevelopmentSafetyPanel` is exported for family/branch pages and included in Progress/Coaching; it uses this projection without expanding coach access to `children`.
- Migration `20260920004427_product_training_guidance.sql` adds the current instruction table/view and assessment `next_target`, then wraps the existing dispatcher. Regenerate database types after both new migrations. Add `development.safety` to the Owner's permission selection UI.
- Validator and table exports: `developmentSchema`, `developmentTables` from `lib/platform/development.ts`.
- `public.development_sessions()` supplies coach-safe session/athlete identifiers and names, no family contact or commercial details. Root product GET exposes it as `data.development_sessions`. `can_coach` separates a reviewer's visibility from a current assignment.
- `private.development_coach_session(uuid)` is the current assignment predicate. The subsequent academy migration extends it for explicitly active, unrevoked temporary substitutions.
- `private.development_parent(uuid)` is the family ownership predicate for development reads. Child-scoped guardian restrictions must be applied here when enabled by community permissions.
- Permission names: `development.configure`, `development.review`, `development.publish`, `development.certify`. Head Office role is required in addition to grants; Owner has the shared AAL2 authority. Configure uses a global grant. Coaches may draft only within a current assignment without broad record grants.
- `DevelopmentPanel` uses `ProductProps` and sections `progress`, `coaching`, `criteria`, `reports`, `certificates`; `developmentArabic` must be merged into shared `useLocale`. It uses loaded `sport_levels`, `children` where permitted, and safe projected coach student names. Parent/child/sport filters cover assessment, report, result, history and certificate collections.
- UI download URL: `/api/product/certificates/[id]`; the authorized handler should return `application/pdf`, a safe generated attachment filename and `Cache-Control: private, no-store`.
- `certificatePdf(row, arabicFontBytes?)` returns `Promise<Uint8Array>`. Required row fields: `reference`, `recipient_name`, `sport`, `level_name`, `title`, `issued_at`. Supply the self-hosted `public/fonts/noto-sans-arabic-certificate.ttf` bytes for Arabic names. Worker-safe module: no filesystem, network or Node Buffer in rendering code.

## Certificate evidence and license

`pdf-lib@1.17.1` and `@pdf-lib/fontkit@1.1.1` create actual landscape PDF pages. Fontkit GSUB/GPOS shaping plus individually positioned PDF glyphs preserves connected Arabic and vowel/hamza placement. Text is fitted to page width, with logical-start English and logical-end Arabic placement. The PDF contains the immutable issue reference and date, not family/contact identifiers or internal notes.

The existing Arabic WOFF2 shaped correctly but produced invisible glyphs when embedded by this library; actual rendered output exposed that defect. The certificate uses the original TTF from the official [Google Fonts Noto Sans Arabic distribution](https://github.com/google/fonts/tree/main/ofl/notosansarabic). The unmodified SIL OFL 1.1 license is stored beside it as `noto-sans-arabic-certificate-LICENSE.txt`. No runtime external font call is made.

Validated a generated Arabic example including `أَحْمَد محمد` by rendering with Poppler and inspecting the image. QA scratch artifacts are under `/tmp/kafou-development-pdf`, not production content. Arabic and Latin text are supported; arbitrary other scripts are not claimed.
