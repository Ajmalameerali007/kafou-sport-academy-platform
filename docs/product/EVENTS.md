# Synthetic events and dated camps

Events remain separate from memberships, normal classes, class delivery and payments. An event can be a one-off date (`synthetic-one-off-v1`) or a configurable camp (`synthetic-camp-v1`). These are explicit synthetic defaults, not approved operating or legal policies. No payment is collected. The camp has 2–30 non-overlapping dated occurrences within a 90-day span; each lasts at most 12 hours within one Dubai calendar day. Capacity (1–100 children), branch, sport, assessed level, age group and exact synthetic waiver are common to the camp. Venue and coach are selected separately for each date. Dates and resource assignments are immutable after creation: cancel a future date, or cancel and create a replacement timetable.

An active MFA-ready Super Admin, or Admin/Branch user with current branch access and explicit `events.manage`, creates or cancels an event. Coach and Sales roles cannot manage events merely by receiving that permission. The branch must be confirmed, active and offer the sport. Each camp coach must have an active Coach profile and current permission for that branch; mixed Sales/Coach profiles are excluded. The venue must belong to the branch. Registration rechecks live coach and venue availability. An authorized event scheduler gets only coach ID, name and authorized branch from `event_coach_directory`.

An active parent selects one to eight distinct children from one currently owned family and explicitly accepts the event's exact waiver for each child. All selected siblings register for **all scheduled camp dates** together or none do. Registration and sibling-batch cancellation close at the original first start, including when that date is later cancelled. Every child's age is checked on every remaining date, along with assessed sport level, existing class/trial/makeup participation and other registered event occurrences. Registration links the family to the branch; branch staff must retain that link and branch authorization to read family-linked event records.

The event row and shared operational transaction lock serialize capacity checks. The unique active event/child index prevents duplicates. Each sibling retains a separate immutable consent snapshot containing the guardian, exact document version/body, acceptance time and the accepted occurrence IDs, dates, venues and coaches. Existing pre-camp consent records keep an empty schedule snapshot rather than inventing past acceptance. Cancelling one future date leaves the remaining dates and registrations intact, releases its resources and notifies current guardians. Cancelling every remaining unfinalized date closes the event. Whole-event cancellation releases registrations while preserving consent, corrections and finalized attendance history. Notifications are in-app records; no external delivery provider is activated.

Camp resources cannot overlap noncancelled class sessions, including substitute-coach assignments, or other open event occurrences using the same venue or coach. Guards also reject later regular-session creation/movement, class coach/venue reassignment, or substitute assignment that would take a camp resource. Later child roster placement or session movement cannot overlap **any** registered camp date. Booking availability uses that same full timetable. Legacy one-off events retain their earlier class-sharing behavior; however, a new one-off cannot occupy a reserved camp venue.

Each registered child gets an unmarked attendance row for each scheduled occurrence. Authorized event staff, or the assigned active Coach with `attendance.finalize` for that branch, can save marks after the date starts. Finalization requires the date to have ended and every active child to have an explicit `present`, `absent`, `late` or `excused` mark. No attendance value implies class delivery, makeup credit, invoice or coach payment. Parents see only finalized attendance for their currently owned children. Coaches use the minimal `event_attendance_register` projection: dated child identifiers/names and marks, without family, guardian, contact or consent records. Coach access ends on assignment/event cancellation, branch/role/profile revocation, or 90 days after the occurrence, as part of the explicit synthetic access rule. Those current assignment changes also invalidate cached coach-command receipts.

Finalized marks cannot be overwritten through the save command. Authorized event staff can make a reasoned correction; the prior mark, new mark, actor and time remain in an immutable correction record visible to the current owning family. Whole-event cancellation preserves finalized marks and their corrections even when registrations become cancelled. A revoked guardian loses this history immediately. Direct authenticated writes to event tables are denied.

## Contracts and evidence

- Original migration: `20260920003857_product_events.sql`. Additive camp migration: `20260920021338_product_event_camps.sql`.
- `lib/platform/events.ts` exports `eventCommands`, `eventRegistrationSchema`, `campCreateSchema`, `eventAttendanceSchema` and `eventTables`. The existing `events` command dispatch is reused.
- New commands: `events.camp.create`, `events.occurrence.cancel`, `events.attendance.save`, `events.attendance.finalize`, `events.attendance.correct`. Creation takes `occurrences[{venue_id,coach_id,starts_at,ends_at}]`; attendance takes `occurrence_id` and unique `entries[{registration_id,attendance}]`; correction takes attendance row `id`, new `attendance`, and `reason`.
- New tables: `event_occurrences`, `event_attendance`, `event_attendance_corrections`. Invoker views `event_attendance_register` and `event_coach_directory` use fixed-search-path definer projections with explicit live authorization. The coach directory has a unique row `id` and a separate `coach_id` to submit.
